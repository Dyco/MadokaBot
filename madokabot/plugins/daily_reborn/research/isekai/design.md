# 异世界投胎：数据与接入方案草案

本文件保留实现前的设计提案。当前实现采用显式关联池，未采用第5节的条件接口示意；实际运行格式以 [数据包说明](../../../../../assets/json/daily_reborn/isekai/README.md) 为准，运行资料已统一放入 assets/json/daily_reborn 并通过核心 JsonDataStore 读取。调研依据和缺口见 README.md、sources.json，catalog.json 仍是资料目录而非生产配置。

## 1. 与现有模块的关系

已阅读 daily_reborn 的入口、命令、模式、持久化、事务服务、模拟、属性、潜力与渲染代码。

| 现有文件/职责 | 现状 | 异世界接入建议 |
| --- | --- | --- |
| matchers.py / commands.py | 四个模式的指令与会话处理 | 新增入口，遵循 COMMAND_START，注册显式 use_cmd_start=True |
| modes.py | world/china/japan/usa | 追加独立 isekai 模式，世界家族放在该模式内部 |
| models.py | 各模式每日结果表＋公共进度表 | 新增异世界每日表，不修改旧表名与旧结果 |
| service.py | 免费、积分重开、锁、历史 | 复用事务流程，明确区分模拟器和历史摘要 |
| simulation.py | 按出生人口选地区，生成现实属性 | 保留现实职责，异世界使用独立模拟模块 |
| render.py / reborn.html | 依赖国家、人口、地图和现实潜力 | 新增异世界渲染与模板，不伪造国家字段 |
| attributes.py / potential.py | 五项星级与现实成长路线 | 可复用纯展示工具，不直接套用现实职业成长文案 |
| data | 人口与地图资料 | 新增独立数据子目录，不往人口文件塞虚构国家 |

现有 history_entry、record_birth、render 的若干入口都依赖 country、score、label；这属于明确需要适配的业务耦合，不能仅加一个模式字符串。

优先在 daily_reborn 内进行局部、显式分派：现实模式继续使用原模拟器，isekai 使用新模拟器；历史摘要分别组装。无需将四类世界内容放到 core，也无需为这一个功能建立跨插件框架。

可考虑新增 madoka_daily_reborn_isekai_record，进度以 RebornProgress.mode = isekai 区分。这只是建议名称；真正落地后保持稳定，不触动原有表与持久化键。所有世界家族共用异世界模式的每日机会，是否接受该产品规则仍待确定。

## 2. 稳定的结果结构

通用层只保留跨世界有相同含义的信息；每个世界再提供自己的扩展字段。

| 字段 | 含义 |
| --- | --- |
| result_version | 结果结构版本 |
| dataset_version | 本次使用的数据包版本 |
| mode / world_id / setting_id | 指令模式、世界家族、具体规则包 |
| date | 上海时区的抽取日期 |
| birthplace | 地区标识、展示名、环境标签 |
| household | 家庭模板、生活条件、可获得的资源 |
| parents | 父亲、母亲的身份记录 |
| child | 物种、祖源、出生状态和先天条件 |
| development_directions | 有条件的未来发展方向，不表示已达成 |
| rarity | 项目定义的出身稀有度 |
| display_snapshot | 本次展示文案与关键标签快照 |

不能把各世界的“力量”做成同一条 1—100 数轴。可用 power_system_id、rank_id 保存原世界含义：

- D&D：职业、职业等级分栏；普通人可以没有冒险职业。
- 赛博：专业能力、装备、维护和权限分栏；不将所有人硬塞进等级表。
- 修仙：境界与境界内层次分栏；凡人是未修炼状态。
- 诡秘：途径与序列分栏；普通人没有序列，序列数字越小越强。

界面可共用“力量/技术概况”的展示槽位，但不计算跨世界战斗力排名。

建议保存最终结果快照，重复查看与历史展示直接读快照。资料更新不重抽、不用新版标签重写旧人生；规则包版本供追溯。历史可记录“世界＋地区＋物种＋家庭摘要”，不再要求 country_code。

本期不强制复用五项星级。若后续保留，家境应来自家庭资源，资质来自独立抽样，安全来自环境与风险；避免父母身份与完全独立抽出的家境星级互相矛盾。确定计分之前，优先展示各维度事实。

## 3. 父母身份：先确定关系，再抽具体条件

建议固定抽取顺序：

1. 世界家族与规则包。
2. 出生地区及其资源、物种、力量范围。
3. 家庭模板：确定亲子种族组合、家庭类型和双方身份范围。
4. 父母的生计/身份与当前实力，受前面条件约束。
5. 家庭可获得的资源与出生环境。
6. 孩子的先天条件、特殊出身及发展方向。

家庭模板承担关联关系。例如同族普通家庭、跨阶层家庭、单方修炼家庭、双方修炼家庭，均通过显式配置表达，不先独立抽出两个不相容的父母再无限重抽。

父母基本信息建议：

| 字段 | 用途 |
| --- | --- |
| role | 父亲或母亲 |
| presence | 可知且在场、缺席、身世未知等资料状态 |
| species_id / lineage_id | 物种和祖源；不记录人名 |
| occupation_id | 日常生计 |
| social_position_id | 社会身份或职务 |
| affiliation_kind_id | 宗门、企业、教会、行会等组织类型 |
| power_system_id / power_rank_id | 当前力量体系与层次 |
| resource_access_ids | 对家庭能提供的条件 |

“身世未知”表示信息未知，不能暗中自动设为高阶血统。双亲缺席时可以有监护条件；如首期不做，就不在池中加入这种家庭模板。

孩子不直接继承父母职业、修为、义体或配方。继承只通过已定义的兼容表和先天特征表发生；资源则由家庭条件推导。没有核验的遗传机制不启用。

初期只覆盖已整理清楚的父母关系。人工生命、克隆、心智实例化等未来改用 origin_relations 表达生物父母、养育者、制造者或心智来源；不能为了显示整齐，给所有生命强造一个生物学父亲和母亲。

## 4. 数据包目录与扩展范围

建议的生产目录（尚未创建）：

    assets/json/daily_reborn/isekai/
      manifest.json
      sources.json
      high_fantasy/
        setting.json
        species.json
        occupations.json
        power_ranks.json
        regions.json
        families.json
        traits.json
        events.json
      cyberpunk/
        ...
      cultivation/
        ...
      occult_industrial/
        ...

manifest 显式列出启用的数据包路径和版本。每个包有稳定 ID、中文展示名、数据版本、原作范围、来源引用及可用状态。可以新建世界家族或规则包后只更新 manifest；加载器按相同结构读取，不为每个世界增加 Python 分支。

不必在首版建出所有空文件。先根据实际使用的类别拆分，避免只有几条记录却制造很多层目录。

每个生产条目的最小字段：

| 字段 | 约定 |
| --- | --- |
| id / label | 稳定标识与中文显示名 |
| description | 简短中文解释 |
| tags | 供有限条件过滤的标签 |
| weight | 项目游戏权重，不是原作统计；禁用项不参与池 |
| enabled | 是否允许出现在正式结果 |
| source_refs | 来源 ID；原创条目可为空但必须标注原创 |
| evidence_kind | 原作摘要、项目改编、原创或待核验 |
| requires | 固定格式的条件 |
| effects | 有限的资源/标签影响 |

对有层次的数据使用独立有序表，如境界 order；不要靠中文名称排序，也不要硬编码“筑基就是2”到业务代码中。

## 5. 条件接口保持有限，避免注入式规则

JSON 是数据，不保存 Python、SQL、脚本表达式、可导入函数路径或可执行模板。建议仅支持明确列举的操作：等于、属于集合、数值范围、包含标签、全部满足、任一满足。字段引用只允许来自已知上下文字段。

下面是格式示意，不是已经定稿的运行时协议。所有数值权重均为示例，不能当成既定概率：

    {
      "id": "high_fantasy.family.human_craft",
      "label": "人类工匠家庭",
      "description": "以城镇手工业为主要生计的家庭。",
      "enabled": true,
      "evidence_kind": "project_adaptation",
      "source_refs": ["dnd_origins"],
      "weight": 1,
      "requires": {
        "all": [
          {"field": "world_id", "op": "eq", "value": "high_fantasy"},
          {"field": "region.tags", "op": "has_tag", "value": "settled"}
        ]
      },
      "parent_species": {
        "father": "high_fantasy.species.human",
        "mother": "high_fantasy.species.human"
      },
      "child_species_pool": [
        {"id": "high_fantasy.species.human", "weight": 1}
      ],
      "parent_occupation_pools": {
        "father": ["high_fantasy.occupation.smith"],
        "mother": ["high_fantasy.occupation.scribe"]
      },
      "household_tags": ["craft_access", "basic_literacy"]
    }

示例 smith、scribe、settled 等是预期生产包中的待建 ID，不存在于本轮资料目录；示例不应被静态资料校验当成已存在的条目引用。家族模板与职业表实际落地时再共同定义。

处理方式是先按硬条件缩小候选池，再对可用权重归一化后抽取。跨族出生通过显式的子代池确定；不定义通用“平均父母物种”算法。相同条件下的权重也不能称为最终整个人生的抽中概率。

首版不提供无限重试、任意表达式求值、内容缺失后偷偷切换世界或自动填充高稀有度父母。资料包内的空候选池应作为数据错误被指出。

## 6. 权重、资源与展示

四类世界不存在共同可靠的出生人口数据库。因此只使用项目定义的游戏权重，世界选择可以先提议等权，正式数值在内容审阅后确定。

不把“稀有”等同“好”。罕见血统、特殊出身、危险暴露可以同时带来机会和限制；社会阶层、天赋、成长安全分别展示。世界包可对普通家庭保持足够覆盖，避免全员贵族、巨企高层或修仙大能。

家庭资源优先按模板和职业组合查表生成，不在多个环节重复给同一个条件加分。父母身份有解释作用，例如识字渠道、工坊接触、修炼指导、医疗保障；不会保证孩子未来成就。

建议卡片主要展示：

    世界家族 / 具体规则包
    出生地区与环境
    物种与祖源 / 出生状态
    父亲：物种 · 生计/身份 · 当前力量
    母亲：物种 · 生计/身份 · 当前力量
    家庭资源
    先天条件
    可能的发展方向
    当前的主要限制或隐患
    数据包版本 / 项目游戏设定说明

游戏卡片避免展示规则解释器、数据文件路径和来源审核状态等维护细节；来源放文档或详情中。没有合理依据时不展示精确到小数点的“人生总概率”。

## 7. 自动扩展接口的真实边界

在已有语义中，这些更新可以只改 JSON：

- 添加世界包、地区、普通职业、种族与祖源。
- 添加境界或序列目录、家庭模板、已核验的亲子组合。
- 调整权重、启用状态、条件、资源标签、先天特征和文案。
- 补充来源、注明版本与时代、撤下存在争议的条目。

这些更新仍可能需要代码设计：

- 新增条件运算、资源结算方式、关系语义或交互流程。
- 从出生卡扩展为逐年人生模拟。
- 新增无法用既有结构表达的特殊诞生与遗传系统。

“自动扩展”建议指离线生成或整理候选 JSON，再经过来源与结构审阅发布；不在用户每次抽取时实时联网编设定。抓取网页、模型补充、发布更新是不同步骤，不自动执行未授权的发布任务。

本轮 sources.json 与 catalog.json 已提供来源和证据分类，便于以后制作导入工具。未新增抓取服务、定时任务、数据库迁移或动态脚本加载。

## 8. 校验约束

遵循仓库约定：显式 UTF-8 读写；本轮只进行文档与 JSON 的静态检查，不新增或执行测试。

后续实现时，必要的静态资料检查包括 JSON 语法、ID唯一性、引用有效性、条件操作是否在允许列表、数值权重合法性，以及启用模板是否有完整候选关系。不编写额外测试程序，不运行模拟抽样验证。

本方案保持业务内容在 daily_reborn 内，不要求核心层引用业务插件；也不要求使用注入式写法。若后续发现必须改变框架边界或偏离现有设计，应先明确问题并与用户讨论，再写入功能代码。
